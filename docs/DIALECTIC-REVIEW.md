# 全项目辩证审阅：正题 · 反题 · 合题（2026-10-08）

> 方法：先立正题（肯定现状与成绩），再作反题（自我否证：假设现状是错的，
> 逐项找反例与证据），最后合题（本期修复哪些、延期哪些、为什么）。
> 证据基线：`432 passed + 12 subtests`；三套端到端工具（完整性/渠道/邮件）全绿；
> 对抗审计报告见 `SELF-AUDIT.md`。

## 一、正题：这个项目做对了什么

1. **安全的授权底座**：PBKDF2-SHA256（60 万次）口令、`auth_version` 令牌失效、
   HMAC 请求签名 + nonce 防重放、Ed25519 响应/离线签名、会话密钥 AES-GCM 落库、
   attest 白名单 + `release_id` 绑定、密钥轮换与发行包卫生门禁。
2. **可靠的投递与数据**：邮件/渠道 outbox 具备租约回收、指数退避与 dead 终态；
   发送成功与状态落库拆分，避免重复投递；审计日志控制字符清洗；崩溃日志与
   定时器护栏；数据库在线备份与完整性校验。
3. **完整的功能面**：卡密全生命周期、批次、1:1 门户账号与邮箱登录、SMTP 邮件引擎、
   7 指标告警规则引擎与事件生命周期、Webhook/钉钉/企微/飞书四渠道、AI 助手、
   Python SDK（可嵌入第三方宿主程序）。
4. **可验证的工程**：432 个测试 + 12 subtests；三套端到端验收脚本；发布包
   只含 exe + 签名清单（8 个文件），构建自动拒绝 config/db/私钥。

## 二、反题：自我否证——现状哪里经不起推敲

### A. 架构：单文件巨石与写路径重复

- `server/api.py` 约 137KB、`core/database.py` 约 131KB、`verification/ui.py` 约 87KB、
  `core/pages.py` 约 80KB。路由、校验、业务、渲染混在一起，单点回归面巨大。
- 同一套写操作（生成/吊销/冻结/删除）在 HTTP API、AI 工具、订阅调度三处各自
  调用 DB，缺少统一领域服务层；改一处规则需要人工同步多处。
- 反例：AI 工具直接执行写操作（见 C 安全残余），正是"多写路径"带来的治理漏洞。

### B. 数据层：会随规模与时间退化

- 时间统一存本地字符串 `%Y-%m-%d %H:%M:%S`，跨时区/夏令时语义脆弱。
- 迁移仍是"加列"模式，没有 schema 版本表、回滚与重建表策略。
- 日志/事件/验证码/outbox 历史无保留策略（`purge_logs` 定义后无人调用）。
- 日志搜索为五列 LIKE 全扫 + OFFSET 分页；告警引擎每条规则每周期重复算 7 项指标。
- 反例：服务器界面即使降到 10 秒刷新，仍每次 `count_logs`，表大后周期占用 CPU。

### C. 安全：仍有三处"承认但不甘"

- **AI 写操作一步到位**：模型可在同一轮对话里吊销、冻结、批量删除卡密甚至创建
  主控账号。唯一"确认"在系统提示词里，提示注入可以绕过——这是数据损坏面。
- **attest 信任客户端自报哈希**：改包客户端可以上报白名单里的旧哈希；纯客户端
  方案无法根治，只能靠"缩短发布有效期 + 服务端裁决"抬高成本。
- **渠道域名只做字面 IP/localhost 检查**：域名解析到内网的情况未拦截（为避免慢
  DNS 阻塞 API 而妥协）；需要部署侧配合或引入异步校验。

### D. 可靠性：三处会以"用户可感知的故障"出现

- **完整性门禁硬退出**：清单缺失或被同步工具改坏时直接 `SystemExit(1)`，
  没有只读模式或 `--repair-manifest` 修复通道；一次文件同步事故 = 全部端不可用。
- **AI 任务不可取消**：客户端关闭窗口后，QThreadPool/轮询最长可驻留 600 秒；
  服务端 ThreadPoolExecutor 运行中任务同样阻塞退出。
- **批量操作可重入**：`processEvents()` 期间可再次点击或关闭窗口，几千条吊销
  可能在半完成状态下中断，UI 与服务端状态不一致。

### E. 工程：好测试被 CI 浪费，依赖不锁版本

- CI 只跑 `python -m unittest discover`，而仓库存在大量 pytest 风格用例；
  它们不在 CI 覆盖内（本地全量通过不代表 CI 通过）。
- `requirements.txt` 七个依赖全部不锁版本；`pydantic`/`fastapi` 升级可能直接
  改变运行时行为（P1 期间就出现过 pydantic 校验器写法的问题）。
- 版本号在 `core/config.APP_VERSION` 与 `server/api.VERSION` 两处硬编码，存在漂移风险。
- 文档数量多且层层叠加（C1/P1/A5/A7/BUGFIX/SELF-AUDIT/IMPROVEMENT），缺一个总索引。

### F. 业务与产品：离"可运营"还有距离

- 续费是"请求 + 邮件 + 人工"，没有支付；代理商/返佣、Web 后台、多语言 SDK 未做。
- 单机 SQLite 部署形态决定了并发上限；上服务器需要评估迁移。
- 客户端协议（HMAC/Ed25519/离线码）没有独立的对外规范文档与跨语言测试向量。

## 三、合题：本期动手修什么（四路并行）

| 路 | 修复内容 | 为什么现在做 |
|---|---|---|
| A | AI 写操作两阶段确认（预览 → 短时效令牌 → 执行）+ AI 任务取消与有界退出 | 反题 C/D 中最可能造成真实数据损坏与"关不掉的程序" |
| B | 数据保留定时任务 + 告警指标按窗口缓存 + 新发布自动失效旧 release_meta + 日志计数缓存 + 版本单一来源 | 反题 B/E：延缓规模退化、收回旧构建、消除版本漂移 |
| C | 批量操作忙碌互斥 + `--repair-manifest` 修复通道 + 头像客户端限尺寸解码 | 反题 D：把"必现故障"变成"可修复故障" |
| D | 依赖锁版本 + CI 显式跑 pytest + 文档总索引 | 反题 E：让本地通过等于 CI 通过 |

## 四、合题：明确不做与原因（反对为了动作而动作）

- **不拆巨石文件**：拆分 `api.py`/`database.py` 需要专属阶段（服务层 + 契约测试 +
  灰度），与本期安全修复混做会放大回归面；列入下一阶段重构计划。
- **不引入 FTS5**：当前数据规模（几万级）用现有索引足够；先加计数缓存与保留策略，
  等日志过十万再上 FTS，避免过度工程。
- **不接支付、不做多语言 SDK**：属于产品/商务决策与外部依赖，本轮只固化协议出口。

## 五、验收标准

- 全量测试与三套端到端全部通过；
- AI 删除/吊销类操作在没有确认令牌时返回"待确认"而不是执行；
- 关闭 AI 页面后进程退出时间有上界（不再被 600 秒轮询拖住）；
- 维护任务可跑通且不误删活跃数据；
- 发布包卫生检查通过，重新打包指纹与 release_id 记录在案。
